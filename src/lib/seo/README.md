# SEO + GEO

Everything search engines, AI answer engines, social previews and LLMs see:
`<head>` metadata, Open Graph / Twitter cards, JSON-LD, icons, web manifest,
`robots.txt` (with an AI-crawler policy), `sitemap.xml`, `llms.txt`,
`llms-full.txt` and IndexNow pings.

## Setup (checklist)

1. **Identity**: [`seo.const.ts`](./seo.const.ts) holds the name (and its
   unaccented `alternateName`), the one-sentence bio, region and country,
   target roles, theme color, Twitter handle, `llmsDetails` and the
   `aiCrawlers` policy. The **Profile** global supplies the headline,
   languages and skills of the `Person` JSON-LD; the **Site settings**
   global supplies the email and the public profiles (`sameAs`).
2. **Icon**: replace `src/app/(frontend)/icon.svg` (square, simple, readable
   at 16px), then run `pnpm generate:icons` (pass `--bg "#hex"` if the theme
   color changed). This rewrites `favicon.ico`, `apple-icon.png` and the
   manifest PNGs.
3. **Share images**: `public/og-image.png` is the general one (the headline
   on the site's card). Case studies, chapters, writing entries and Craft
   pieces get their own, generated (see [Share images](#share-images)).
4. **Env**: set `NEXT_PUBLIC_SERVER_URL` to the real origin and
   `INDEXNOW_KEY` in production.
5. After launch: verify the domain in Google Search Console and Bing
   Webmaster Tools with DNS TXT records, then submit
   `https://<domain>/sitemap.xml` in both.

Editors control per-document title, description and share image in each
document's **SEO** tab. Titles are stored bare ("About"), and the layout

"Alejandro Mejía · <Profile headline>", without the template.

## Share images

Every page shares the same card: a mono label, the title and description on
the left, the home page's halftone shape on the right, and the name and
domain at the bottom.

- **General pages** use `public/og-image.png` (the headline and bio).
- **Case studies, chapters, writing entries and Craft pieces** get a card
  with their section and title at `/og/<page path>/<version>.png`. The card
  builders (`og/og-cards.ts`) are shared by the page metadata
  (`generatedShareImage(path, card)`) and the route, so both agree on the
  text. Only published content has one, so the URL can't print arbitrary
  text.
- **The version** is a short hash of the card's text, in the path. Social
  platforms cache a preview by its image URL, so a new title or description
  gives a new URL they fetch again on the next share; editing the body keeps
  it. It only appears in the `og:image` tag, never in a page URL. The route
  answers only the current version (404 otherwise).
- **An image in the document's SEO tab** replaces the generated one.

**Caching.** Each card renders once, on the first request for its path, and
is served from Next's cache after that (incremental, `force-static` with no
paths at build, so the build needs no database). Its CMS read carries the
`cms` tag, so publishing a change discards the cached card and the next
request draws it again. Cards from the Work mock stay until the next deploy.
`next dev` renders on every request, so caching only shows in a production
build.

**Text limits.** `SHARE_CARD_LIMITS` (60 characters for the title, 140 for the
description, three lines each) is the most the card fits. Work, Writing and
Craft cap their title and summary / excerpt / description fields at it, so
an editor can't save text that breaks the card. The renderer also clamps
every line (the title steps down to 52px past 48 characters), so text the CMS
doesn't cap, like the mock or a long case study name in a chapter's label,
ends in an ellipsis instead of running into the shape or the byline. Keep
balanced wrapping off: in `next/og` it breaks the line clamp.

The renderer (`next/og`) can't run a canvas, so the shape is a still,
`og/og-shape.png`, drawn once with the same code as `HalftoneShape`. The
fonts are TTF copies of Geist and Geist Mono (OFL) in `og/`, since `next/og`
can't read the woff2 files the site loads. Redraw the shape and
`og-image.png` together if the card design changes.

## Keeping sitemap and llms.txt fresh

Both are generated from the CMS, not written by hand. They render per request
from data cached under the `cms` tag (`CMS_CACHE_TAG` in `src/lib/cms/cms.const.ts`),
which the content hooks (`src/payload/hooks/revalidate.ts`) expire on publish,
unpublish and delete. No script or rebuild is needed.

`llms.txt` follows [llmstxt.org](https://llmstxt.org). It is a site title, a
summary, your hand-written `SITE.llmsDetails`, and then a link list of every
published page and post with its SEO description. Good SEO descriptions give
a good `llms.txt`.

## GEO (generative engine optimization)

AI answer engines (ChatGPT Search, Claude, Perplexity, Google AI Overviews,
Copilot) choose sources to cite from pages they can fetch, parse and trust.
What the code does for that:

- **Crawlable by AI bots.** `robots.txt` has explicit groups for AI search
  bots (`OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`, …) and training
  bots (`GPTBot`, `ClaudeBot`, `Google-Extended`, …). Both are allowed by
  default. Blocking training is Alejandro's call and doesn't hurt
  citations. Blocking *search* bots removes the site from AI answers.
- **Server-rendered HTML.** Most AI crawlers don't run JavaScript. All CMS
  content is in the initial HTML. Keep it that way: never gate content
  behind client-only rendering. Animation should start from content that is
  already in the DOM.
- **Clean document structure.** One `<main>` landmark (in `PageTransition`),
  one `<h1>` per page (`PageHeader`, or a visually hidden one on Home that
  repeats the sidebar's name and headline), and post bodies limited to h2–h4. `<article>`, `<time>`
  and `<nav>` are used where they apply.
- **Machine-readable facts.** JSON-LD entities are linked by `@id`
  (Person ← WebSite ← WebPage/BlogPosting), with the author, topics
  (`articleSection`) and dates. The site is a person's, so there is no
  `Organization` node.
- **Freshness.** `dateModified` in JSON-LD, a visible "Updated" date on
  articles, accurate sitemap `lastmod`, and IndexNow pings on every publish.
- **LLM-native formats.** `/llms.txt` (curated index) and `/llms-full.txt`
  (whole site as Markdown in one fetch).

What the code can't do (editorial):

- Open each page/section with a direct, self-contained answer to the question
  it targets, then expand. AI engines quote passages, not pages.
- Use descriptive question-style headings, short paragraphs, lists and tables
  for comparisons. Include specific numbers, dates and sources.
- Keep one bio everywhere: `SITE.description`, `llmsDetails`, the Profile
  intro, LinkedIn and GitHub say the same thing. Home and the CV do the job
  of an About page; real profiles in Site settings become the `sameAs` links.
- Write every SEO description by hand. They feed search snippets, social
  cards and both llms files.
- Mark up only content that is visible on the page and cleared for
  publishing (client names), and never review stars about yourself.
- Get mentioned elsewhere (LinkedIn, GitHub, talks, guest posts, cross-posts
  with a canonical link). AI engines weigh third-party corroboration heavily.

## Adding things

- **New static route** (e.g. `/cv` built in code): add it to
  `staticRoutes` in `src/app/sitemap.ts` and export
  `buildMetadata({ title, path })` from the route.
- **New content collection with public URLs**: add a `<name>Path()` helper in
  `seo.utils.ts`, include it in `site-index.server.ts`, use `buildRevalidateHooks`
  on the collection, and add it to the SEO plugin's `collections`.
- **More JSON-LD types** (`ProfilePage` on `/cv`, `Article` for case studies,
  `VideoObject` for clips): reference the Person with `personRef()`,
  add a builder to `json-ld.ts` and render `<JsonLd data={…} />` in the
  route. Check the result with Google's Rich Results Test.

## Gotchas

- `NEXT_PUBLIC_SERVER_URL` must be the production origin at **build** time.
  Next inlines it, so canonicals, OG URLs and the sitemap use the build value.
- Don't add a `twitter`/`openGraph` object to a route by hand. Use
  `buildMetadata` so the site defaults aren't silently dropped.
- Don't add `opengraph-image.*` files next to CMS routes. File-based OG images
  override the editor's SEO-tab image; use `generatedShareImage()` instead.
